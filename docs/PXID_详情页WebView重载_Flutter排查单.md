## 🔴 现状（已经确定的事实，含证据）

### 1. 那个错误页和转圈，都不是 H5 画的

- 错误页文案「网络有问题，请稍后重试 / 重新尝试 / ←」**在 H5 全仓库 grep 不存在**；H5 自己的错误态文案是「内容不存在或已下架」，样式也不同 → **是 Flutter 原生的 WebView 加载失败页**。
- 转圈同样不是 H5 的：H5 `index.html` 里只有空 `<div id="app">`，**没有任何内联 spinner**；详情页的加载态是**带顶栏的灰条骨架**（`fd-skel`）；H5 全部 spinner 只存在于 车辆体检页 / 结算页 / 下拉刷新小圆点。
- 无头浏览器实测线上详情页**首帧（120ms）**：`hasTopBar=false, hasSkel=false, hasSpinner=false, bodyText=''` → **纯空白**。
- H5 只向 Flutter 发两类消息（`ToFlutter_H5OpenFeedDetail` / `ToFlutter_H5OpenFullscreen`），**没有任何「页面就绪」回调** → 可以确定：**App 不是在等 H5 的信号**，它只能靠 WebView 自身的加载事件/超时来判断。

### 2. 真实现象是「反复重载一个已经加载成功的页面」

nginx 访问日志（`/www/wwwlogs/appin.site.log`）实测，多个 IP 出现同一种模式：

| 时间（2026） | 来源 IP | 实际发生的事 |
|---|---|---|
| **09-19 19:50:38–19:50:58** | `49.90.8.1` | 首次加载成功 → 19:50:39 所有 chunk 200（**含最新构建 `FeedDetailView-32xj02nH.js`**）→ 19:50:40 起 `?lang=zh` **每 1~2 秒重载一次，共 10 次** |
| 09-19 18:51–18:53 | `49.90.8.1` | 同款模式，25 次 |
| 09-19 17:47–17:55 | `49.90.8.1` | 同款模式，60 次 |
| 09-18 16:38:56–16:40:08 | `49.90.129.139` | 每 2 秒一次，约 25 次 |
| 09-18 16:43 | `122.96.32.187` | 12 秒内重试 9 次 |

关键点：

- 每次重载请求**全部 304 成功**（内容没变，走的是缓存），期间**子资源全 200**；
- **09-19 19:12–19:52 期间，pxid-h5 全站 4xx/5xx = 0**（144 个 200、22 个 304、1 个 206）；
- 重载期间的接口（`/feed/:id`、`/feed/:id/comments`、`favorite`）与图片**全部正常响应** —— **页面渲染和数据都是好的，整页却仍被反复推倒重来**；
- 重试若干次后停止，随即出现原生错误页（用户看到的「转圈很久 → 网络有问题」）。

> 19:50 那一次尤其关键：**它用的已经是包含今天全部 H5 优化的最新构建**，依然在 18 秒内重载了 10 次。

### 3. H5 与服务器侧今天（09-19）完成的优化

| # | 优化内容 | commit | 效果 |
|---|---|---|---|
| 1 | 公开读接口不再串行等 token（`peek` + token 缓存） | `791e198` | 真机上桥调用只发生一次；公开读零等待 |
| 2 | `peek` 等待宽限 400ms → 80ms | `055c746` | 首屏数据到位提前 ~300ms |
| 3 | 首屏预取从「20+ chunk 并发」改为「等 window load 后串行」 | `791e198` | 不再跟首屏抢连接/带宽 |
| 4 | 图片上传前压缩（最长边 1920 / JPEG q82）+ 历史图批量重压 | `196ec1b`/`39cfb93` | 详情页大图 **3.2MB → 161KB**；历史 10 张 18.5MB → 1.61MB |
| 5 | `/uploads/` 改为 1 年 `immutable` 缓存（原为 `no-store`，每次进页面重下） | nginx | 第二次打开图片零下载 |
| 6 | `index.html` 加 `preconnect` 到 `pxid-api.appin.site` | `196ec1b` | 首次接口省一次 TLS 握手（实测首次 TTFB 235ms → 复用后 40ms） |

### 4. 优化后的实测数据

| 指标 | 实测值 |
|---|---|
| 公网（等同手机）→ 服务器 TTFB | **37~41ms**（静态 index 33~34ms） |
| 服务端 `/auth/token` | **42ms**（直连测量，非排队值） |
| 后端 `pxid-feed` 错误日志 | **最近 4 天 0 条新增** |
| 详情页（热缓存，等同用户日常） | Vue 挂载 **549ms** / 数据到位 **1058ms** / 墙钟 **1088ms** |
| 详情页（冷启动，全新 WebView） | 4G 下 ~4.9s（其中探针环境 TCP 建连就占 1.1s） |
| 带宽 / 负载 | 下载实测 7~21MB/s、load 0.05、0 丢包 |

**结论：H5 侧 1 秒出头即可渲染完成，网络与服务端合计约 40ms，资源零 404、接口零错误 —— 现有的 H5 现象无法解释「转圈十几秒后报网络错误」。** 这个重载循环只可能由 App 侧发起。

## 🟠 问题或卡点

我们卡在「无法从 H5 侧观察到 App 的判定逻辑」，具体三个未知：

1. **判定判据是什么**：App 用什么信号确认「这个 WebView 加载成功了」？`onPageFinished` / `onLoadStop`？某个 JS 回调？还是「DOM 是否有内容」？
2. **重载由谁发起**：什么条件下触发重新加载？超时阈值多少？重试几次、间隔多少？错误页在什么条件下显示？
3. **为什么判失败**：页面明明已经渲染成功（日志显示资源全部 200/304），App 却认为失败 —— 是事件没收到，还是收到的时机不满足它的条件？

> 特别提示（可能直接就是根因）：**详情页是 hash 路由**（`https://appin.site/nav/pxid-h5/?lang=zh#/feed/228`）。哈希变化**不会触发新的页面加载事件**。如果判定逻辑依赖「URL 改变」或「DOM 内容非空」这类信号，详情页/回退场景很容易被误判为「加载失败」。

## 🟢 怎么做（建议方案 + 我们能配合的）

### 方案 A（改动最小）：放宽判定，且「收到加载事件后就不再重载」

- 真机实测 H5 首屏渲染：**热缓存 ~1.0~1.5s**、**冷启动（新 WebView）3~6s**，弱网叠加后会更长。
- 建议：**就绪阈值放宽到 ≥ 8 秒**（覆盖冷启动 + 弱网，这是正常水平而非异常）；
- 更关键：**一旦收到 `onPageFinished` / `onLoadStop`，就立即取消 loading，不要再用固定时长轮询去判定失败**；
- **不要**用「DOM 是否为空」「URL 是否变化」这类判据（见上方 hash 路由提示）。

### 方案 B（更稳，推荐；H5 侧可配合实现）

新增一个「H5 页面就绪」桥消息，沿用现有 channel 风格：

| 项 | 约定 |
|---|---|
| 注入方式 | Flutter 注入 `window.ToFlutter_H5PageReady`（与 `ToFlutter_H5OpenFeedDetail` 相同方式） |
| 发送时机 | H5 **首屏数据渲染完成后**（详情页 = 正文与图片区渲染完成） |
| payload | `JSON.stringify({ route: '/feed/228', ms: 1058 })` |
| Flutter 行为 | 收到 → 关闭 loading 占位；**在收到之前不发起重载** |
| 兜底 | 若 8 秒仍未收到，再按超时逻辑处理（避免 H5 异常时永久转圈） |
| 覆盖范围 | 详情页 `/feed/:id` + 其余全屏白名单页（可分批） |

> 这个 H5 侧实现量很小（半天内可交付并上线）。你们确认要，我们就直接做。

### 顺带两个小问题（方便的话一起看）

1. **`appin.site/p9-api/feed/1/favorite` 反复 404**
   该路径不是 H5 发的（H5 全部走 `pxid-api.appin.site`）。`/p9-api/` 是服务器上另一个服务（电摩 H5 `nav/pxid-emoto/` 在用），ToC App 不该调它 → 疑似 App 原生侧接口地址配错（全局搜字符串 `p9-api` 即可确认）。

2. **安卓 WebView 右侧的原生滚动条**
   H5 已在 CSS 全局隐藏滚动条，但**安卓 WebView 的页面级滚动条是原生绘制的，CSS 关不掉**。请在承载 H5 的 WebView 上关闭：
   - `flutter_inappwebview`：`InAppWebViewSettings(verticalScrollBarEnabled: false, horizontalScrollBarEnabled: false)`
   - 官方 `webview_flutter`：`AndroidWebViewController.setVerticalScrollBarEnabled(false)`
   需要覆盖所有承载 H5 的 WebView（发现/精选/服务根页 + 详情全屏页）。
